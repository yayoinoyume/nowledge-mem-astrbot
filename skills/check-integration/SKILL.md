# 记忆自检

## 何时使用
- 用户问「记忆是不是坏了」「为什么搜不到」「怎么配的」「状态正常吗」
- `nowledge_mem_search`、`nowledge_mem_save` 返回 `error:`
- 搜索结果长期为空，分不清是没有记忆还是没连上
- 刚改过配置、换过空间、接进新环境

## 第一步：看状态
调用 `nowledge_mem_status()`，按返回值分三种情况处理。

### 连不上
返回 `connected: false`，`error` 指向不可达、超时或拒绝连接：
- 先确认记忆服务本身在运行
- 再确认配置里的服务地址（`api_url`）从当前环境能访问，协议、主机、端口都对
- 两处都正常仍然连不上，把 `error` 原文交给用户，不要换端口、换地址去试

### 鉴权失败
返回里出现 401、403，或提示凭据无效：
- 凭据缺失或过期，只有用户能补
- 不要反复重试同一个失效凭据，也不要从别处找凭据
- 明确说「凭据无效或已过期」，不要笼统说成「网络问题」

### 正常
`connected: true` 且没有 `error`：进入第二步。不要因为空间名、身份名看着陌生就判定配置错了。

## 第二步：用具体词验证真的能读
用最近确实聊过的具体名词搜一次，例如 `nowledge_mem_search(query="上周那个登录态迁移", limit=5)`。

- 返回条目：读写链路正常，把命中的 `id` 给用户
- 返回 `no matches: query="..."`（且没有 `error:`）：链路正常，只是这次查询没匹配到。这是「没搜到」，不是「坏了」
- 返回 `error:`：回到第一步，按错误类型说明

只验证一次。不要连换五个关键词，把自己绕进「到底哪一步坏了」。

## 哪些会自动发生，哪些要靠模型自觉
| 行为 | 谁负责 | 控制项 |
| --- | --- | --- |
| 每轮注入上下文包（含工作记忆） | 插件自动 | 配置项 `enable_bundle` |
| 每轮按当前消息召回记忆 | 插件自动 | 配置项 `enable_recall` 与条数上限 |
| 会话消息落库成对话线程 | 插件自动，每轮增量同步 | 配置项 `enable_capture`；失败会留下待重试批次 |
| 把结论保存成记忆 | 模型主动，或用户提醒 | 没有自动机制：没人开口、模型也没判断值得存，就不会有新记忆 |
| 更新已有记忆 | 模型主动 | 同上 |

自检时先按这张表分清责任：搜不到新结论，多半是「没人保存过」或「模型没主动存」，而不是链路坏了。

## 常见故障对照
| 现象 | 常见原因 | 怎么处理 |
| --- | --- | --- |
| 搜不到 | 空间不对、关键词太抽象、服务端索引还没就绪 | 换具体词再搜一次；仍为空就问用户是不是在别的空间里存的；不要改配置 |
| 保存了但看不到 | 写进了别的空间，或读取用的是不同空间 | 对比写入与读取的 `space` 是否一致；不一致就是两份互不相通的记忆 |
| `nowledge_mem_get` 报 404 | `memory_id` 不属于当前空间，或 id 已失效 | 用搜索重新取 id，不要继续拿旧 id 试 |
| `nowledge_mem_thread_show` 返回空 | 该会话还没落库，或 `thread_id` 不是当前会话的 | 说清「还读不到」，不要编造消息条数；下一轮同步后再看 |
| 状态正常但 `pending` 不落 | 写入侧受阻 | 提醒用户检查服务与网络，不要循环重试 |

## 硬规矩
- 不要为了「让它看起来正常」而编造接口、端点或返回内容
- 不要顺手改配置、换空间、重启服务来「修好」；这些要用户明确同意
- 没真正验证过就说「还没确认」，不要说「已修复」
